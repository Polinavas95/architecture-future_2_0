1. Разделение системы на домены

| Домен                      | Владелец                    | Содержание                                                                            | Обоснование                                                                                                                   |
|----------------------------|-----------------------------|---------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------|
| Клиники                    | Клиники                     | Записи к врачам, инвентаризация, персонал (без медкарт), счета за услуги (не кредиты) | Операционная деятельность клиник — высоконагруженная, критична к задержкам; отделение от аналитики ускоряет работу операторов |
| Медицинские данные         | Клиники (медицинская часть) | Медкарты, истории болезней, снимки, результаты исследований                           | Врачебная тайна; не должна смешиваться с аналитикой или финтехом; доступ только врачам и ИИ-сервисам                          |
| Финтех                     | Финтех-компания (банк)      | Кредиты, счета клиентов, платёжная история, финансовые транзакции                     | Банковская лицензия требует отдельного контура безопасности и отчётности; может развиваться независимо от медицины            |
| ИИ-сервисы                 | ИИ-компания                 | Модели, результаты диагнозов, скоринги, предсказания                                  | Быстрая итерация моделей не должна зависеть от DWH; ИИ читает обезличенные медицинские данные и публикует результаты          |
| Управление / Головной офис | Головной офис               | Агрегированные KPI, финансовая отчётность (сводная), дашборды                         | Единая точка сбора аналитики для руководства; питается из доменов, но не содержит их первичных данных                         |
| Партнёры                   | Интеграционная группа       | Данные от фарм-компаний, производителей электроники                                   | Отдельный домен для внешних партнёров (данные могут приходить в разных форматах, не нарушая основные домены)                  |
|                            |                             |                                                                                       |                                                                                                                               |

Обоснование с бизнес-спенариями

1) Запуск нового финтех-продукта (например, "кредит на лечение")
Старая архитектура: нужно менять DWH (добавлять поля, таблицы, процедуры), согласовывать с медицинским доменом, ждать релиза.
Новая архитектура: финтех-домен получает через Kafka событие "пациент создан" (только ID и сумма счёта, без медкарты). Разрабатывает кредитный продукт внутри своего домена;

2) Новая ИИ-модель для распознавания снимков
Старая архитектура: нужно выгружать снимки из DWH, результат загружать обратно, писать ETL.
Новая архитектура: ИИ-домен имеет прямой доступ к домену «Медицинские данные» через защищённый API. Результаты публикует в Kafka, откуда их забирают нужные сервисы. DWH не участвует.

3) Подключение фармацевтической компании
Старая архитектура: ESB на Camel требует настройки новых маршрутов, DWH — новых таблиц для хранения данных поставок.
Новая архитектура: фармацевтическая компания подключается к Kafka через коннектор. Домен «Партнёры» обрабатывает их формат, публикует нормализованные события. Основные домены могут подписаться или игнорировать.

3. Аргументация и преимущества для бизнеса

| Аспект                        | Старая архитектура                                           | Новая архитектура                                                       |
|-------------------------------|--------------------------------------------------------------|-------------------------------------------------------------------------|
| Зависимости                   | Любое изменение требует изменения DWH                        | Домены независимы, общаются через события                               |
| Производительность            | Отчёты формируются часами из-за пересекающихся трансформаций | Витрины строятся независимо; можно масштабировать каждый домен отдельно |
| Безопасность                  | Медицинские данные и финансы в одной БД — риск утечки        | Домен "Медицинские данные" изолирован полностью                         |
| Время вывода нового продукта  | 2-3 месяца (изменить DWH, протестировать, выкатить)          | 2-3 недели (работа внутри одного домена, интерфейс через API/события)   |
|                               |                                                              |                                                                         |

Обоснование с бизнес-спенариями

1) Ускорение вывода финтех-продуктов
Финтех-команда не ждёт релизов DWH, а может сама развивать свой домен;
2) Итеративное улучшение ИИ-диагностики
ИИ-команда может каждый день обновлять модели и A/B тестировать их на реальных снимках.
DWH не тормозит — ИИ читает медицинские данные напрямую (через API с контролем доступа);
3) Подключение партнёров (фарма, электроника) без большой нагрузки
Не нужно менять ядро системы, так как партнёрский домен сам разбирается с форматами.
4) Быстрая отчётность для руководств
Домен "Управление" строит агрегаты из событий Kafka в real-time; отчеты берутся из маленьких витрин за секунды

К дополнительным бизнес-выгодам можно отнести:
- Независимые команды: каждый домен может иметь свой технологический стек. Финтех на Go/Java, ИИ на Python, Клиники на C#/Node.js;
- Устойчивость: падение одного домена (например, Kafka-кластера для партнёров) не останавливает работу клиники или банка — они продолжают свою операционную деятельность;
- Data Mesh готовность: предложенная модель соответствует принципам Data Mesh — данные как продукт, доменная ориентация, самообслуживание.
