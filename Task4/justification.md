Предварительные требования
1. Установить Terraform (если ещё не установлен)
```shell
brew tap hashicorp/tap
brew install hashicorp/tap/terraform
```
2. Установить Yandex Cloud CLI (опционально, для поиска образов)
curl https://storage.yandexcloud.net/yandexcloud-yc/install.sh | bash
source ~/.zshrc
yc init
3. Создать SSH-ключ (если нет)
ssh-keygen -t rsa -b 4096 -f ~/.ssh/id_rsa -N ""
4. Получить OAuth-токен в Yandex Cloud 

Настройка тераформ конфигурации

Создать файлы конфигурации
main.tf, variables.tf, outputs.tf

Создать файл с переменными
```shell
cat > terraform.tfvars << 'EOF'
cloud_id      = "ваш_cloud_id"        # из консоли Yandex Cloud
folder_id     = "b1gshns20ibb0q9347hv" # ваш folder_id
token         = "y0_AgAAAAA..."        # ваш OAuth-токен
db_password   = "YourStrongPass123!"

zone         = "ru-central1-a"
environment  = "dev"
project_name = "future20"
vm_image_id  = "fd845dr9j4h2aaq1m6ko"  # актуальный ID Ubuntu 22.04
EOF
```

Инструкция по тестированию
1. Инициализация Terraform
```shell
terraform init
```
2. Просмотр планируемых изменений
```shell
terraform plan
```
3. Применение конфигурации (создание инфраструктуры)
```shell
terraform apply -auto-approve
```
4. Вывод выходных параметров
```shell
terraform output
```
5. Уничтожение инфраструктуры (опционально)
```shell
terraform destroy -auto-approve
```

## Обоснование конфигурации инфраструктуры

1. Выбор ресурсов и параметров

Виртуальная машина (app)
- 2 vCPU, 4 GB RAM: минимальная конфигурация для тестирования приложения (для прода может быть увеличена до 4 vCPU / 8 GB RAM).
- Boot Disk 20GB HDD: для ОС (Ubuntu 22.04)
- Data Disk 100GB SSD: для данных приложения (логи, временные файлы, кэши). SSD выбран для производительности.

Управляемая PostgreSQL
- s2.micro (2 vCPU, 8 GB RAM): обеспечивает ~3000 IOPS и достаточную память для кэширования запросов (для dev-окружения можно уменьшить до s2.small (1 vCPU, 4 GB)).
- 50GB SSD: минимальный размер для managed БД в Yandex Cloud (для ПРОМа — 100-200GB в зависимости от объёма медицинских данных (аналитика без карт)).
- Версия PostgreSQL 15: стабильная

NAT и сеть
- NAT Gateway с таблицей маршрутизации: позволяет приватной подсети (БД) выходить в интернет для обновлений, но не имеет публичного IP
- Публичная подсеть (для VM приложения): имеет прямой выход в интернет (nat = true) для SSH и API.
- Приватная подсеть (для БД): недоступна из интернета, только из публичной подсети на порту 5432.

Группа безопасности
- Разрешён входящий SSH (22), HTTP (80), HTTPS (443) отовсюду — для тестов.
- PostgreSQL доступен только из подсети приложения (10.0.1.0/24).
- В production нужно ограничить SSH по IP-адресам администраторов.

Сервисный аккаунт
- Используется для доступа VM к managed БД и к Object Storage (без хранения ключей в коде приложения).

Почему декларативный подход (IaC)?

- Воспроизводимость: инфраструктура описывается кодом -> можно развернуть идентичную среду (dev/stage/prod) без ручных шагов и ошибок.
- Версионирование: изменения инфраструктуры проходят code review через Git, есть история и возможность отката.
- Автоматизация: одна команда `terraform apply` создаёт всю сеть, VM, БД, группы безопасности. Без IaC инженер потратил бы 2-3 часа на кликах в веб-консоли.
- Документация: сам код является документацией (какие ресурсы, с какими параметрами).
- Управление состоянием: Terraform отслеживает зависимости (например, сначала сеть, потом VM).
  При удалении ресурса `terraform destroy` корректно удаляет всё в обратном порядке.

3. Воспроизводимость и масштабирование

Воспроизводимость
- Remote backend (S3): state-файл хранится в бакете, вся команда работает с одним состоянием.
- Переменные (terraform.tfvars): разделение кода и конфигурации — можно менять окружение, не трогая код.
- Модули (в перспективе): можно вынести VM, БД, сеть в отдельные модули и переиспользовать.

Масштабирование
- Горизонтальное: увеличение количества VM через `count` или `for_each`.
- Вертикальное: изменение параметров ресурсов (cores, memory, disk_size) — Terraform пересоздаст их с новыми параметрами.
- Региональное: копирование конфигурации в другую зону доступности (меняем `zone` и `subnet`).

4. Альтернативы и почему не выбраны

| Альтернатива                      | Почему не подходит                                                                  |
|-----------------------------------|-------------------------------------------------------------------------------------|
| Ручное создание через web-консоль | Невоспроизводимо, возможность появиления ошибок, нет истории                        |
| Ansible без Terraform             | Ansible хорошо для настройки ПО, но плохо управляет сетью, дисками, БД как сервисом |
| CloudFormation (AWS)              | Необходимо облако в России                                                          |
| Pulumi (программируемый IaC)      | Избыточно для данной задачи, команда знает HCL                                      |

5. Безопасность и соответствие требованиям

- Чувствительные данные (токены, пароли) не хранятся в коде, передаются через переменные (sensitive = true).
- State-файл: хранится в зашифрованном бакете с включённой версионизацией (можно откатиться).
- Группы безопасности: минимально необходимые порты (принцип least privilege).
- Приватная БД: не имеет публичного IP, доступна только из приложения.
